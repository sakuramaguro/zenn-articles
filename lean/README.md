# Lean 4形式化本の検証環境

段階0で検証環境と原稿の対応表を整備し、段階1-Aで偽の等式・未証明部分・ゴール表示の説明を、段階1-Bで合成の仮定・擬距離と商・閉球のコンパクト性を修正しました。段階1-Cでは、不動点の一意存在・具体的な値・反復列の収束を本文と演習に揃えました。段階1-Dでは、ディリクレ関数の可積分性と収束定理の仮定・呼び出しを修正し、第17章の演習解答を検証しました。段階2では導入と第1〜5章の型・証明・型クラス・探索・次元定理の説明を修正し、この範囲の全112ブロックを完成例・連結例・意図した失敗・演習の穴に分けて検証しました。段階3-Aでは第6・7章の連続性・近傍・距離を修正し、全89ブロックを検証しました。段階3-Bでは第8・9章の位相・コンパクト性・完備性を修正し、全64ブロックを検証しました。対象は `books/lean4-formalization` の全23本のMarkdownです。初回の421ブロックに説明用の例と確認コマンドを3個追加し、現在は424ブロックを記録しています。

## 再現手順

Git、Python 3.10以降、elanを利用できる状態で、このリポジトリの `lean/` に移動します。

```sh
cd lean
lake exe cache get
python3 scripts/catalog.py extract
python3 scripts/verify.py
```

elanは `lean-toolchain` に書かれた版を使用します。初回の依存関係とビルドキャッシュの取得にはネット接続とディスク容量が必要です。`lake exe cache get` はMathlibのビルド済みファイルを取得します。原稿の検証は続く `verify.py` が行います。通常の検証で `lake update` は実行しません。

`verify.py` は原稿との対応、取得済み依存リポジトリのコミットと追跡ファイルの変更、Leanの版を確認し、`lake build` と `Audit.lean` の公理検査を実行します。さらに、原稿から抽出した例のエラー・警告・公理一覧を照合します。記録は `.generated/verification.json` と `.generated/logs/` に保存されます。検査に失敗したときは成功記録を残しません。

対応表だけを確認する場合は、LeanやMathlibの取得前でも次を実行できます。

```sh
python3 scripts/catalog.py check
```

検査スクリプト自体の変更時は `python3 scripts/test_validation.py` も実行します。コードの欠落・変更や、文脈参照の欠落、未確認の公理を成功扱いしないことを確認します。

掲載コードのビルド対象は計302ブロックです。途中の断片は指定された順に連結します。章別ファイルは原稿のimportを維持し、名前の衝突を防ぐ名前空間を追加しています。`BEGIN SOURCE` と `END SOURCE` の間は原稿からの抽出内容と照合します。Baselineは今後の修正に使う参照例で、現在の本文と一致するという意味ではありません。

警告をビルドエラーとして扱います。主要な宣言については `sorryAx` だけでなく、未確認の公理への依存も検出します。許容する標準公理は `propext`、`Classical.choice`、`Quot.sound` で、各宣言が使うものをログに記録します。検査対象の追加時には `Audit.lean` も更新します。

`catalog/index.json` の `diagnostics` に34件の照合対象を記録しています。偽の等式は指定した2件のエラーが出ること、`sorry` の例は警告と `sorryAx` が出ること、完成例は掲載した公理一覧が得られることを確認します。第1〜5章の意図したエラー9件・未完成13件、完成例の公理2件に加え、第11章の連続性の仮定不足による失敗と、縮小性の演習の穴も確認します。第6・7章の意図したエラー2件と未完成の演習2件も加えています。第8・9章の未完成の演習4件も加えています。単にコンパイラが失敗しただけでは検査の成功としません。

これらは原稿のコードを抽出し、それぞれ独立したLeanプロセスで実行します。未完成例には警告を観察するため `-DwarningAsError=false` を指定しますが、完成例のビルドと公理検査の基準は変えません。未証明の宣言を `LeanBook` の完成例へimportしません。

| 練習問題・未完成の骨格 | 未完成であることを表示し、完成解答と別に管理する。 |
| 説明用の抜粋 | 実際の定義・型・出力と照合し、省略を明示する。 |

分類は掲載目的を表します。不備のある完成解答を未完成例に分類し直して、修正対象から外すことはしません。各ブロックの `fixture` は原文を保存するファイルで、検証成功を保証するものではありません。断片の `context.blocks` は文脈や置換位置の参照です。同じ証明を説明する複数の段階を単純に連結する指示ではありません。`preceding_setup` は先行するimport/openの位置情報で、先行例の局所変数が有効だと保証する情報ではありません。

初回421ブロックの一次点検は各ブロックに `import Mathlib` を補って独立実行したものです。正常終了232件のうち24件にsorry警告、エラー189件でした。変更したコードの過去の点検結果には元のIDと内容ハッシュを添え、新しいコードの動作確認と混同しないようにしています。この記録は切り分けの参考に限り、証明数や原稿の誤りの件数として扱いません。

## 段階1以降の更新方法

1. `catalog/issues.json` から対象指摘を選び、本文・予告・再掲・演習を合わせて修正します。
2. 完成例を章別Leanファイルに追加し、`LeanBook.lean` にimportします。原稿と対応する宣言には `compiled_mappings` とソースマーカーを付けます。
3. 原稿の変更に合わせ、`catalog/chapters/章名.json` の位置・内容ハッシュ・分類・文脈を確認して更新します。原稿全体のハッシュ、章別ファイル一覧、ビルド対象との対応は `catalog/index.json` に記録します。ブロックの追加や削除でIDが変わる場合、文脈参照と指摘の参照も更新します。自動的に成功扱いへ変更しません。
4. `catalog.py extract` で原文の抽出先と表を再生成し、`verify.py` で検証します。必要な主要宣言を `Audit.lean` に追加します。
5. 指摘の完了条件を満たしたものだけ、解消した変更と検証記録を添えて状態を更新します。

本文の変更やコードの取り違えを見逃さないよう、対応表はMarkdown全23本のハッシュとコードごとのハッシュを検査します。本文だけの変更でも確認が必要です。段階6では全完成例と意図的なエラーを含む最終検証、Zennの全ページ表示確認、継続的な自動検査を揃えます。
