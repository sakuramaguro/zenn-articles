# 第3章：Claudeを使った型エラー突破術 〜エラーと友達になる日まで〜

紙の上なら5秒で書き終わる当たり前の証明に、Lean 4では平気で1時間を溶かしました。振り返ると、Leanの文法や型に慣れていなかったことに加え、AIに診断に必要な情報を伝えられていない場面もありました。本章では、その失敗から質問と検証の手順を見直します。

本章のコードは本書の固定環境で確認しています。完成例は、記載した前提を含めて実行してください。意図したエラー例・`sorry` を残した演習は別ファイルに置きます。画面の画像は執筆時の記録で、以下のテキスト出力は説明のために型引数や表示名を省略した要約です。

## 3.0 本章のゴール ──── ゴール逆算型アプローチ

まず本章の終着点を見ていきます。以下の3つを達成することが本章のゴールです。

```lean:完成例・確認コマンド
import Mathlib

-- ゴール①：rfl が失敗するケースを自力で読み、ring で修正できる
-- 数学：a + b = b + a（交換法則）/ Lean：rfl では解けない、ring や Nat.add_comm を使う
example (a b : ℕ) : a + b = b + a := by
  ring
  -- No goals ✓

-- ゴール②：型クラスエラーを自力で読み、[Add α] を追加して修正できる
-- 数学：「型 α に足し算は定義されているか？」/ Lean：[Add α] という免許証が必要
section
variable (α : Type) [Add α] (a b : α)
#check a + b  -- a + b : α

-- ゴール③：sorry で作った骨格を、実際の証明で埋められる
-- 数学：未証明の課題を切り分け、一つずつ証明する
-- Lean：以下は sorry を取り除いた完成例
theorem skeleton (a b c : ℕ) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c := by
  have step1 : a ≤ b := h1
  have step2 : b ≤ c := h2
  linarith
  -- No goals ✓
end
```

「なぜ `rfl` が使えないのか」「型クラスの免許証とは何か」「`sorry` をどう戦略的に使うか」——これらを一つずつ見ていきます。

## 3.1 `rfl` の罠 ──── 定義的等値という最初の壁

まずは軽いジャブから。足し算の交換法則（`a + b = b + a`）の話です。

```lean:意図的なエラー例
import Mathlib

theorem add_comm_simple (a b : ℕ) : a + b = b + a := by
  rfl
```

この証明の実況中継をしてみましょう。

**ステップ①：`by` の直後でのゴール確認**

```text
-- by 直後の InfoView
a b : ℕ
⊢ a + b = b + a
```

「自然数 `a`, `b` に対して `a + b = b + a` を証明せよ」というゴールです。

**ステップ②：`rfl` を試みる**

しかし、無慈悲にもLean 4から突き返されました。

![rfl失敗のエラー画面](https://storage.googleapis.com/zenn-user-upload/571065a5753e-20260324.png)
*図3-1：自然数の加法の交換法則に`rfl`を使い、失敗した画面です。*

```text
-- InfoView に表示されるエラー
Tactic 'rfl' failed: The left-hand side a + b is not
definitionally equal to the right-hand side b + a
```

**ステップ③：エラーを読む**

ここで登場する **"definitionally equal"（定義的に等しい）** という概念が、Lean 4を理解する上での最初の関門です。

`rfl` の正体は「左辺と右辺が定義を展開するだけで同一になる」ときに使えるタクティクです。`a + b` と `b + a` は代数的変形を経なければ一致しません——だから `rfl` は使えないのです。

**ステップ④：正しいタクティクで修正する**

```lean:完成例・確認コマンド
import Mathlib
-- 失敗例とは別ファイルで実行する完成例。
theorem add_comm_fixed (a b : ℕ) : a + b = b + a := by
  ring
```

```text
-- ring 適用後の InfoView
Goals accomplished!
```

`ring` に変えるだけで証明が通ります。

`rfl` が使える条件と使えない条件を表にまとめます。

| 等式の種類 | `rfl` が使えるか | 正しいタクティク |
|-----------|:--------------:|----------------|
| `0 = 0`（同一） | ✅ | `rfl` |
| `1 + 1 = 2`（数値計算で同一） | ✅ | `rfl` または `norm_num` |
| `a + b = b + a`（代数変形が必要） | ❌ | `ring` |
| `a ≤ a + b`（`a b : ℕ`） | ❌ | `omega` または `Nat.le_add_right a b` |

:::message
**💡 わざとエラーを出してみよう**

以下は意図的なエラー例です。自然数について、同じ偽の等式を二つのタクティクで試します。

```lean:意図的なエラー例
import Mathlib

example : (1 : ℕ) + 1 = 3 := by rfl
example : (1 : ℕ) + 1 = 3 := by norm_num
```

`rfl` は左右が定義的に等しくないため失敗します。`norm_num` も証明を完成させられず、この例では `False` がゴールとして残ります。自然数の命題 `1 + 1 = 3` 自体が偽なので、タクティクを変更しても正しい証明にはなりません。

主張を訂正すると、次の否定は証明できます。上のエラー例とは別のファイルで実行するか、上の例を削除して置き換えてください。

```lean:完成例・確認コマンド
import Mathlib

theorem one_add_one_ne_three : (1 : ℕ) + 1 ≠ 3 := by
  norm_num
```

エラーを読んだら、タクティクだけでなく、主張・型・仮定が意図どおりかも確認しましょう。
:::

:::message
**🔗 [第5章](ch05)への伏線①**

[第5章](ch05)の次元定理では、最終ステップで `omega`（自然数・整数の等式・不等式を自動解決する専用エンジン）を使います。`ring` と `omega` の「守備範囲の違い」が、あの証明のクライマックスで重要な意味を持ちます。

## 3.2 AIへの質問 ──── 文脈不足と誤った提案への対処

`rfl` の罠を抜け出した私を次に待ち受けたのが、Lean 4で最も頻出し、最も心を折るエラー—— **「Application type mismatch（引数の型不一致）」** です。

まずはシンプルな例で構造を理解していきます。

```lean:意図的なエラー例
import Mathlib

def add_five (n : Nat) : Nat := n + 5

-- 数学：add_five に文字列を渡す（型の不一致）
-- Lean：Nat を期待しているのに String を渡している
#eval add_five "hello"
```

**ステップ①：エラーの構造を確認する**

本書の固定環境で、上の `import Mathlib` を含むコードを実行した診断の本文です。ファイル名・行番号・診断の接頭辞を省いています。

```text
Application type mismatch: The argument
  "hello"
has type
  String
but is expected to have type
  ℕ
in the application
  add_five "hello"
```

![型不一致エラー画面](https://storage.googleapis.com/zenn-user-upload/b2bc302415eb-20260324.png)
*図3-2：執筆時に撮影した型不一致の画面です。自然数を受け取る`add_five`に文字列を渡しています。固定環境の表記は上のテキストを参照してください。*

**ステップ②：エラーを解剖する**

この出力では、見出しに続く実際の型・期待する型・対象の式まで読むと、何が食い違っているか分かります。

| 出力の一部 | 意味 |
|-----------|------|
| `Application type mismatch` | 関数の引数の型が合わない |
| `"hello"` と `has type String` | 渡した引数と、その実際の型 |
| `expected to have type ℕ` | 関数が要求する型。`ℕ` は自然数型 `Nat` の記法 |
| `in the application` 以下 | 問題の起きた式 `add_five "hello"` |

**ステップ③：原因を特定し修正する**

ここでは「自然数に5を足す」という意図を保ち、入力を自然数に直します。文字列を読み取って計算したい場合は、文字列の解析と、解析に失敗した場合の処理を別に設計する必要があります。エラーの種別だけで修正方法が一つに決まるわけではありません。

```lean:完成例・確認コマンド
import Mathlib
-- 3.2節の失敗例と置き換えて実行する。
def add_five_fixed (n : Nat) : Nat := n + 5
#eval add_five_fixed 7
-- 出力：12
```

このシンプルな例なら原因はすぐ分かります。しかし、これが何行も続く証明の中で発生すると、原因を見失いやすくなります。

### 「丸投げ」が生んだ最大の失敗

ここで私は、**本章で最も恥ずかしい失敗をしました。** パニックになるたびにエラー文だけをコピーして「エラーが出ました。直して」と丸投げし続けたのです。するとClaudeは文脈が分からないまま、**存在しない定理（ハルシネーション）を捏造して返してきました。**

文脈が不足すると原因を絞りにくくなります。ただし、情報を揃えてもAIは誤った定理名や証明を提案することがあります。採用前に固定環境で確認します。

:::message alert
**💀 Claudeに聞くときにやってはいけないこと**

次のような質問では、原因を絞るための情報が欠けています。情報を揃えても、提案された名前・型・証明は手元で確認します。

1. **コードだけ貼り付けて「直して」と頼む**
   → 意図した仮定と結論が伝わりにくくなり、別の命題への変更を提案されることがあります。

2. **エラーメッセージをコピーしない**
   → 実際の型・期待する型・未解決の型変数などが、原因を調べる手がかりになります。番号も含めてエラー全文を渡すと、同じ変数がどこに現れるか追えます。

3. **何を証明したいか伝えない**
   → 「線形写像の核の有限次元性を、どの仮定から示したいか」まで伝えます。意図が曖昧だと、仮定を強めたり、別の結論に変えたりする提案を見落としやすくなります。
:::

### AIへ質問するときの「3点セット」

失敗から学んで辿り着いた結論は、Claudeに質問する際には必ず以下の**3つをセットで渡す**ということです。

| セットの要素 | 内容 | なぜ必要か |
|------------|------|-----------|
| ① コード全体 | `theorem ...` から全文 | Claudeは「何を証明しようとしているか」を知らない |
| ② エラーメッセージ全文 | InfoViewの赤いテキスト全体 | 診断の根拠がエラーの細部に隠れている |
| ③ 数学的意図 | 「○○という事実を証明したい」 | 数学的に正しいアプローチを提案できるようになる |

3点セットの質問テンプレートはこうです。

```
以下のLean 4のコードで型エラーが出ています。

【コード】
theorem ... := by
  ...

【エラーメッセージ】
application type mismatch
  ...

【数学的意図】
○○という事実（数学的には△△定理）を証明したいです。
```

## 3.3 Mathlibの定理が見つからない ──── `Unknown constant` の読み方

「Mathlibに収録されている何万もの定理名を、一言一句違わず全部暗記しなければならないのか……？」

型エラーの次に、名前が見つからないというエラーを調べます。

**ステップ①：エラーの確認**

```lean:意図的なエラー例
import Mathlib

#check Nat.add_comm_wrong
```

固定環境での診断本文です。ファイル名・行番号・診断の接頭辞を省いています。

```text
Unknown constant `Nat.add_comm_wrong`
```

![Unknown constantエラー画面](https://storage.googleapis.com/zenn-user-upload/d0e20bd999d0-20260324.png)
*図3-6：執筆時に撮影した名前解決のエラーです。固定環境の診断本文は上のテキストを参照してください。*

定理名を1文字でも間違えると、Lean 4は「そんな名前は知らない」と突き返します。

**ステップ②：原因を特定する**

名前の誤記、必要なimportや名前空間の不足、使用しているMathlibの版の違い、存在しないAPIの提案などが原因になります。AIが提案した名前も同じ順で調べ、現在の環境での完全な名前と型を `#check` で確認します。名前を解決できないという診断だけでは、定理がどこにも存在しないとは断定できません。

### 救世主となる内蔵タクティク `exact?` と `apply?`

定理名を丸暗記する必要はありませんでした。Mathlibをimportした環境では、ゴールと現在の仮定から証明を探す `exact?`・`apply?` が使えます。

**ステップ①：`exact?` を試す**

```lean:完成例・確認コマンド
import Mathlib

-- 数学：a + b = b + a（交換法則）を自動で探索させる
theorem test (a b : ℕ) : a + b = b + a := by
  exact?
```

**ステップ②：InfoViewに青い提案が出る**

```text
-- InfoView の提案（青い文字）
Try this: exact Nat.add_comm a b
```

![exact?成功画面](https://storage.googleapis.com/zenn-user-upload/6034ff2cab45-20260324.png)
*図3-7：`exact?`が`exact Nat.add_comm a b`を提案した画面です。提案の表示は版や文脈によって変わります。*

青い文字をクリックするだけで、`exact?` という文字が自動的に正しいコードへと書き換わります。

**ステップ③：提案されたコードで証明が完了する**

```lean:完成例・確認コマンド
import Mathlib
theorem add_comm_explicit (a b : ℕ) : a + b = b + a := by
  exact Nat.add_comm a b
```

`exact?` と `apply?` の使い分けを見ていきます。

| タクティク | いつ使うか | InfoViewの変化 |
|-----------|-----------|---------------|
| `exact?` | ゴールを一発で解決したい | `Try this: exact ...` が出る |
| `apply?` | ゴールを変形して前進したい | `Try this: apply ...` または `exact ...` が出る |

## 3.4 型クラスの沼 ──── `failed to synthesize instance` を解剖します

| 式 | 型・意味 |
|---|---|
| `0 : Nat` | 自然数の項 |
| `(0 : Nat) = 0` | `Prop`に属する命題 |
| `h : (0 : Nat) = 0` | その命題を証明する項 |
| `Nat : Type` | 自然数の型 |
| `Prop : Type` | 命題が属する宇宙 |
| `Type u : Type (u + 1)` | 宇宙は階層を持ち、最上位の`Type`はありません |

`Type*`は、新しい宇宙変数を用いた`Type u`を表す記法です。「型＝集合」は理解のための比喩で、Leanの型と`Set α`は同じものではありません。

基礎的なエラーを乗り越え、「任意の型 $\alpha$ の元 $a, b$ について足し算を考える」という設定を書いてみます。

**ステップ①：エラーを確認する**

```lean:意図的なエラー例
import Mathlib

variable (α : Type) (a b : α)

-- 数学：型 α の元 a, b の和 / Lean：α に足し算が定義されているか？
#check a + b
```

```text
-- InfoView のエラー
failed to synthesize instance
  HAdd α α ?m.123
```

![failed to synthesize instanceエラー画面](https://storage.googleapis.com/zenn-user-upload/bbe6380ae5b9-20260324.png)
*図3-8：加法のインスタンスが見つからない画面です。メタ変数の番号は固定ではありません。*

**ステップ②：エラーを解剖する**

エラーメッセージの正体は「`α` という型に足し算（`HAdd`）のインスタンスが見つからない」という宣告です。

Claudeへの3点セット質問の後、返ってきた解説を要約します。

> 「`α` は中身の全く分からない『未知の型』です。そこに足し算（`+`）という操作が定義されている保証はどこにもありません。`[Add α]` という型クラスで明示する必要があります。」

**ステップ③：型クラス（免許証）を追加して修正する**

```lean:完成例・確認コマンド
import Mathlib
-- 数学：「α は加法の構造を持つ」という前提を追加する
-- Lean：[Add α] という型クラスの免許証を提示する
section
variable (α : Type) [Add α] (a b : α)

#check a + b  -- a + b : α
end
```

![型クラス追加後・エラー消滅画面](https://storage.googleapis.com/zenn-user-upload/3093b01750b5-20260324.png)
*図3-9：`[Add α]`を加え、`a + b`の型を確認した画面です。加法の交換律を証明した画面ではありません。*

エラーが消えました。

型クラスとは「型に対する免許証」です。`[Add α]` は「`α` には足し算が定義されています」という免許証を提示することで、Lean 4が自動的に `+` の実装を探し出してくれます。

数学とLeanの対応を表にまとめます。

| 数学の前提 | Lean の型クラス（免許証） | 意味 |
|-----------|------------------------|------|
| $\alpha$ は集合（加法だけ） | `[Add α]` | 足し算が定義されている |
| $\alpha$ は加法可換群 | `[AddCommGroup α]` | 足し算・逆元・可換性が定義されている |
| $\alpha$ は体 | `[Field α]` | 四則演算すべてが定義されている |
| $\alpha$ は位相空間 | `[TopologicalSpace α]` | 開集合が定義されている |
| $\alpha$ はノルム付き加法可換群 | `[NormedAddCommGroup α]` | 加法とノルムの法則を持つ。体上のノルム空間には `NormedSpace` も必要 |

必要な演算や法則を仮定として明示することが、型クラスを理解する出発点です。一つの構造から複数のインスタンスが導かれる場合もあり、宣言数とエラー数は一対一には対応しません。

:::message
**💡 プログラマ向け：型推論との違い**

Leanでも、式の使われ方から型を推論します。それに加えて、演算に必要な構造を型クラス探索で補います。`[Add α]` は呼び出し時に探索される引数を表し、演算の実装を渡します。より強い代数構造では、演算の法則の証明も渡されます。型推論と型クラス探索は、互いに関係しながら働く別の仕組みです。
:::

:::message
**🔢 数学学部生向け：型クラスエラーの数学的意味**

「`failed to synthesize instance HAdd α α`」というエラーは、数学の言葉に翻訳すると「**現在の環境では必要な加法のインスタンスが見つかりません**」という意味です。集合 $\alpha$ に加法の演算を与える前に `a + b` と書こうとしたのと同じことです。`[Add α]` を追加するのは、数学で「$\alpha$ に二項演算を与える」と書くことに対応します。加法群と仮定するには、演算だけでなく群の法則も含む `[AddGroup α]` が必要です。この対応に慣れると、型クラスエラーが「どの代数構造が欠けているのか」を正確に告げてくれる道標になります。
:::

:::message
**🔗 [第5章](ch05)への伏線④**

[第5章](ch05)5.3節では、型クラスの前提を付けずに線形写像の型を書いたときのエラーを確認します。その後、体・加法可換群・加群の仮定をそろえた宣言を組み立てます。個々のエラー数ではなく、各仮定が何を表すかに注目してください。
:::

## 3.5 `sorry` ──── 未証明の箇所を明示する

証明の途中で書き方が分からなくなったときは、`sorry`で未証明の箇所を明示し、全体の構成を先に検討できます。

**ステップ①：`sorry` で骨格を作る**

```lean:未完成の骨格・練習問題
import Mathlib

-- 数学：a ≤ b かつ b ≤ c ならば a ≤ c の証明（骨格版）
-- Lean：sorry で未証明の課題を仮置きする。証明はまだ完成していない
theorem hard_proof (a b c : ℕ) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c := by
  have step1 : a ≤ b := sorry  -- 後で h1 を使う
  have step2 : b ≤ c := sorry  -- 後で h2 を使う
  sorry  -- a ≤ c の最終的な導出
```

**ステップ②：`sorry` を書いた直後のInfoViewを確認する**

```text
-- InfoView（赤ではなく黄色い警告のみ）
declaration uses `sorry`
```

![sorry黄色波線警告画面](https://storage.googleapis.com/zenn-user-upload/69cbbf323933-20260324.png)
*図3-10：`sorry`によって`No goals`になっていても、未証明であることを示す警告が残っています。*

通常の設定では、`sorry` の使用は警告になり、宣言が受理されます。警告をエラーとして扱う設定では、この時点でビルドは失敗します。受理される場合でも、確認できたのは未証明部分を仮置きしたコードの型の整合性です。**残した課題が証明できるとは限りません。**

例えば、`sorry` は偽の命題 `False` も仮置きできます。次はその挙動を確認するための未証明の例で、完成した証明として使うものではありません。別のファイルで実行し、確認後は削除してください。

```lean:未完成の骨格・練習問題
import Mathlib
theorem unfinished_false : False := by
  sorry

#print axioms unfinished_false
```

```text
warning: declaration uses `sorry`
'unfinished_false' depends on axioms: [sorryAx]
```

ここでは `sorry` でゴールを閉じていますが、`False` を証明したわけではありません。`sorryAx` は未証明部分への依存を表しています。

**ステップ③：`sorry` を一つずつ本物の証明に置き換える**

ステップ①の `hard_proof` を次の完成例に置き換えます。同じ名前の宣言を二つ並べないようにしてください。

```lean:完成例・確認コマンド
import Mathlib

theorem hard_proof (a b c : ℕ) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c := by
  have step1 : a ≤ b := h1    -- sorry → h1 に置き換え
  have step2 : b ≤ c := h2    -- sorry → h2 に置き換え
  linarith                    -- sorry → linarith に置き換え
  -- No goals ✓

#print axioms hard_proof
```

```text
'hard_proof' depends on axioms: [propext, Classical.choice, Quot.sound]
```

この完成例には `sorryAx` への依存がありません。表示された三つはMathlibでも使われる標準的な公理です。公理が表示されること自体を未完成とみなすのではなく、何に依存しているかを確認します。詳しくは[Lean公式の公理の説明](https://lean-lang.org/theorem_proving_in_lean4/Axioms-and-Computation/)を参照してください。

`sorry` の戦略的な使い方を表にまとめます。

| 使い方 | 目的 |
|--------|------|
| 証明全体を `sorry` で仮置き | 主張を型として記述できるか確認する。真偽の判定ではない |
| 各ステップを `sorry` で分割 | 未証明の課題を明示し、それぞれ証明できるか検討する |
| 詰まった箇所だけ `sorry` | 他の部分を先に完成させて全体の流れを確認する |

:::message alert
**⚠️ 未証明の例と完成した証明を区別する**

練習問題や説明用の骨格には、未完成と明示して `sorry` を使えます。完成解答として示す例では、`sorry` を取り除き、エラー・警告と主要定理の `#print axioms` を確認します。別の補題に残った `sorry` への依存も確認が必要です。さらに、定義・仮定・結論が意図した数学の主張に対応しているかを読み直します。`No goals` の表示だけでは、これらは判定できません。
:::

:::message
 **🔗 [第5章](ch05)への伏線⑤（最重要）**

[第5章](ch05)5.2節では、核・像の有限次元性と次元等式を `sorry` で仮置きします。前二つは仮定を理解するための確認課題です。完成例では既存の次元等式の補題を直接使い、`sorryAx` への依存がなくなったことを確認します。
:::

## 3.6 まとめ ──── 第3章の全対応表と練習問題

### 型エラーの種類と対処法

数学とLeanの対応を表にまとめます。

| エラーの種類 | 分かること・考えられる原因 | 確認と対処 |
|---|---|---|
| `Tactic 'rfl' failed: not definitionally equal` | 左右が定義的に等しくない | 主張・型・仮定を確認する。真の命題なら `ring` などを検討する。偽の等式はタクティク変更では証明できない |
| `Application type mismatch` | 引数の実際の型と期待される型が合わない | 対象の式と両方の型を読み、数学的意図に照らして入力・関数・型注釈を確認する |
| `Unknown identifier` / `Unknown constant` | 現在の環境で名前を解決できない | 綴り、import、名前空間、版を確認し、完全な名前で `#check` する。候補の探索には `exact?` / `apply?` も使う |
| `failed to synthesize` | 必要な型クラスのインスタンスを見つけられない | 対象の型・演算・import・スコープを確認する。仮定を追加する場合は、元の数学的主張に必要な条件か確かめる |

### 証明の作業フロー対応表

| 数学の作業 | Lean の操作 |
|---|---|
| 証明の全体像を考える | `sorry` で骨格を作る |
| 補題の名前を調べる | `exact?` / `apply?` を使う |
| 型エラーを直す | エラーの3段構造を読む → 3点セット質問 |
| 代数変形の等式を証明する | `ring` |
| 数値計算の等式・不等式を証明する | `norm_num` |
| 線形不等式の推移を証明する | `linarith` |

### 練習問題

以下の3問に挑戦してみましょう。

**問1（易）：以下のコードを入力し、エラーメッセージを読んでください。次に、エラーが出ない正しいコードに書き直してください。**

```lean:意図的なエラー例
import Mathlib
-- 意図的にエラーを出す演習
example (a b : ℕ) : a * b = b * a := by
  rfl  -- これはエラーになります
```

InfoViewに出るエラーを読んで、「エラーの原因は何か」「どのタクティクに変えれば直るか」を考えてください。

:::details ヒントを見る

エラーメッセージに "definitionally equal" という言葉が出るはずです。`a * b` と `b * a` は計算結果として等しいですが、Lean の定義を展開しただけでは一致しません。乗法の交換律を代数的に処理するタクティクを探してみましょう。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib
example (a b : ℕ) : a * b = b * a := by
  ring
  -- No goals ✓
```

エラーの原因：`rfl` は「定義的に等しい」ときだけ使えます。`a * b = b * a` は乗法の交換律という代数的事実であり、定義展開だけでは証明できません。`ring` は可換半環や可換環で多項式の等式を処理するタクティクです。自然数は環ではありませんが、可換半環なのでこの例に使えます。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
example (a b : ℕ) : a * b = b * a := by
  exact Nat.mul_comm a b
```

`Nat.mul_comm` を使えば直接証明できます。`exact?` の提案は版や文脈によって変わることがあります。乗法の交換律は Mathlib に名前付きで登録されており、`exact` で直接提出できます。
:::

**問2（中）：以下のコードで `failed to synthesize instance` エラーが出ます。型クラスを追加して直してください。**

```lean:意図的なエラー例
import Mathlib

-- 任意の型 α の元について、掛け算を考えたい
variable (α : Type) (a b : α)

example : a * b = b * a := by
  sorry
```

このコードでは、`a * b` の型を調べる段階で乗法のインスタンスが不足しています。乗法の構造と交換律の仮定を追加し、`sorry` も証明に置き換えてください。

:::details ヒントを見る

`variable` の宣言自体は受理されます。エラーが出るのは、演算の構造を与えずに `a * b` と書いた箇所です。`a * b` という掛け算を書くためには、`α` が乗法を持つことを宣言する型クラスが必要です。さらに交換律を証明するには、その乗法が可換であることも必要です。Mathlib では `[CommMonoid α]` や `[CommRing α]` などが候補です。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib

-- 数学：α は可換モノイド（掛け算と単位元があり、交換律が成立）
-- Lean：[CommMonoid α] という型クラスの免許証を追加する
section
variable (α : Type) [CommMonoid α] (a b : α)

example : a * b = b * a := by
  exact mul_comm a b
  -- No goals ✓
end
```

`[CommMonoid α]` という型クラスを提示することで、Lean は `*` の実装と `mul_comm` などの定理が自動的に使えるようになります。型クラスという抽象層を一枚挟んだことで、「$\alpha$ が何であれ可換モノイドなら乗法の交換律が成立する」という一般的な事実を証明できます。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
-- CommMonoid では加法・分配法則を仮定していない。交換法則を直接使う。
theorem commMonoid_mul_comm {α : Type*} [CommMonoid α] (a b : α) :
    a * b = b * a :=
  mul_comm a b
```

`CommMonoid` だけでは `ring` に必要な加法や分配法則の構造がありません。ここでは交換法則 `mul_comm` を証明の項として直接使います。`by exact ...` を使う解答と、同じ証明を別の構文で書いたものです。
:::

**問3（難）：以下の証明の骨格を完成させてください。`sorry` をすべて取り除き、完全な証明にしてください。**

```lean:未完成の骨格・練習問題
import Mathlib

-- 数学：任意の自然数 n に対して n^2 + n は偶数
-- 数学的根拠：n^2 + n = n * (n + 1) は連続する2整数の積なので偶数
theorem even_square_plus_self (n : ℕ) : 2 ∣ n ^ 2 + n := by
  sorry  -- ここを埋める
```

詰まったら以下のテンプレートを使ってClaudeに3点セット質問を投げてみてください。

```
【コード】
（上のコード全体を貼り付ける）

【エラーメッセージ】
（InfoViewに出る内容を貼り付ける）

【数学的意図】
n^2 + n = n(n+1) と変形して、連続する2整数の積が偶数であることを使いたいです。
Mathlib に「n * (n + 1) が偶数」を示す補題はありますか？
```

:::details ヒントを見る

`n^2 + n = n * (n + 1)` という変形は `ring` で示せます。次に `Nat.even_mul_succ_self n` で偶数性を示し、`.two_dvd` で「2で割り切れる」という形へ移します。変数同士の積を含むので、線形算術を扱う `omega` だけで解けるとは考えないでください。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib
theorem even_square_plus_self (n : ℕ) : 2 ∣ n ^ 2 + n := by
  -- 数学：n^2 + n = n * (n + 1) と変形する
  have h : n ^ 2 + n = n * (n + 1) := by ring
  -- 数学：n * (n + 1) は連続する2整数の積なので偶数
  rw [h]
  exact Nat.even_mul_succ_self n |>.two_dvd
  -- No goals ✓
```

このタクティクを選んだ理由：`ring` で代数変形を行い、`Nat.even_mul_succ_self` という Mathlib の補題（「$n \times (n+1)$ は偶数」）を直接使う方針です。この補題が返す `Even` とゴールの整除関係をつなぐのが `.two_dvd` です。探索の提案は読み込んだ定理や文脈によって変わるため、ここでは補題を明示します。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
-- 第1解で使った偶数性の補題に、式の変形を合わせる別の書き方。
theorem even_square_plus_self_calc (n : ℕ) : 2 ∣ n ^ 2 + n := by
  have h : n ^ 2 + n = n * (n + 1) := by ring
  simpa only [h] using (Nat.even_mul_succ_self n).two_dvd
```

第1解は `rw [h]` でゴールを先に変形し、この別解は `simpa only [h] using ...` で提出する証明の型とゴールをそろえています。どちらも同じ偶数性の補題を使っています。
:::

## つまずきポイントQ&A

:::message
**📝 第3章 つまずきポイントQ&A**

**Q1. Claudeが返した補題名を使ったらエラーが出た**
→ 名前の誤記、必要なimportの不足、版の違い、存在しない名前の提案などが考えられます。`#check` で名前が見つからない場合は、現在の環境で解決できないということです。`exact?` で自力探索するか、再度3点セットで質問し直しましょう。

**Q2. `apply` と `exact` の使い分けが分からない**
→ `exact h` は、ゴールの証明として `h` を提出します。`apply f` は `f` の結論をゴールに合わせ、まだ与えられていない引数を新しいゴールにします。残る引数がなければ `apply` もそのままゴールを閉じます。

**Q3. エラーメッセージが長すぎて読めない**
→ まず見出しでエラーの種別を把握し、続いて対象の式・実際の型・期待する型を読みます。証明の途中なら、InfoViewの変数・仮定・ゴールも確認してください。後半に期待する型や問題の式が出ることもあるので、最初の1行だけで原因や修正方法を決めません。何を証明したいかと照合し、AIに相談するときはエラー全文を渡します。

**Q4. 型クラスのエラーが出たが、どの型クラスが必要か分からない**
→ `failed to synthesize` に続く型を読み、どの型にどの演算や構造が必要なのかを確認します。型の取り違え、importやスコープの不足、必要な仮定の不足などを調べます。AIにはコード・エラー全文・数学的意図を渡し、「どの原因が考えられ、元の仮定と結論を保ってどう確認できるか」と質問します。エラーを消すためだけに型クラスの仮定を増やさず、追加条件が元の主張に必要か確かめてください。

**Q5. `simp` で証明できると思ったが無限ループした**
→ `simp` は強力ですが、書き換えルールが循環するとループします。`set_option maxHeartbeats 400000 in` でタイムアウト値を上げても解決しない場合は、`simp only [...]` で適用するルールを明示するか、`ring` / `linarith` / `omega` など目的別タクティクに切り替えてください。
:::
