# はじめに

この本は、数学の証明を「機械に検証させる」という体験を、できるだけ正直に記録したものです。

私がLean 4を始めた理由は、大学の授業で証明の穴を何度も指摘されたことでした。「直感的に明らかだ」と思って書いた式変形が、先生の目には根拠のない飛躍として映っていた。悔しかった。そして「人間に詰められる前に、機械に詰めてもらえないか」と考えるようになりました。

Lean 4はその問いに答えるシステムです。書いた証明を、定義・仮定・公理に基づく型検査で確かめます。`Goals accomplished!` は、その位置で未解決のゴールがなくなったことを示す表示です。ただし、未証明の箇所を一時的に埋める `sorry` でもゴールを閉じられます。完成を確認するときは、エラーや警告、公理への依存、書いた命題が数学的な意図と一致するかも確認します。

## 現在の掲載範囲と今後の目標

本書は一冊の中をPart 1〜4に分けています。現在読める本文はPart 1〜3の第1〜18章です。Part 4は執筆予定で、確率微分方程式の定義や解の存在・一意性の証明はまだ掲載していません。

**今後の目標は、確率微分方程式（SDE）の形式化です。**

$$
dX_t = b(t, X_t)\,dt + \sigma(t, X_t)\,dW_t
$$

Part 4では、確率過程や伊藤積分を準備したうえで、この方程式を表現することを目指します。以下は、その前提となる確率空間の宣言例です。

```lean:完成例・確認コマンド
import Mathlib
open MeasureTheory

-- Part 4への準備（予告）：確率微分方程式の登場人物たち
-- 数学：(Ω, ℱ, P) が確率空間、X : Ω → ℝ が確率変数
variable (Ω : Type*) [MeasurableSpace Ω]
         (P : Measure Ω) [IsProbabilityMeasure P]
-- Part 1でこのコードが「何を言っているか」が分かるようになります
```

このコードで宣言しているのは確率空間の前提です。確率変数やSDEの定義・証明はまだ含んでいません。将来の目標と、この宣言で確認できる範囲を区別してください。

Part 1ではLean 4の予備知識を必要としません。初めは型やエラーメッセージを読み解くのに時間がかかることがあります。文法を一度に暗記するより、型・仮定・ゴールを確認し、小さな例で試すことを大切にします。AIの提案も手がかりにしながら、最後は自分の環境で確かめていきます。Part 2以降では、上の表に示した数学の知識を前提とします。

## この本の読み方 ──── 読者層別の案内

:::message
**💡 A：数学学部生の方へ**

型システムに不慣れでも大丈夫です。「型」を「集合」のアナロジーで捉えながら読み進めてください。`Nat` と `Int` は別の型です。ただし整数が期待される文脈では、自然数から整数への変換が自動挿入される場合があります。[第2章](ch02)でその違いを丁寧に解説します。
:::

:::message
**💡 B：プログラマの方へ**

TypeScript・Haskell の型システムの経験があれば有利です。Leanでは命題 `P : Prop` 自体を型として扱い、その型の項 `h : P` を作ることが証明になります。例えば `P` を `1 + 1 = 2` としたとき、この等式は命題であり、証明はその項です。命題と証明項の区別が本書の最初の山場です。[第2章](ch02)を丁寧に読んでください。
:::

:::message
**💡 C：純粋数学者の方へ**

数学の直観は証明方針を立てる助けになります。ただし Mathlib の設計思想（型クラス・宇宙多型）には驚くかもしれません。「なぜこんなに抽象的なのか」という疑問は正当です。第2〜3章でその設計思想を「解剖」します。結論を先に言うと、この抽象層がPart 3と今後のPart 4での再利用性を生んでいます。
:::

## 本書の特徴

本書では、公式ドキュメントも参照しながら、著者がつまずいた箇所と、その原因を調べて解決する過程を紹介します。

本書が一番大切にしているのはその部分です。エラーメッセージを読み、その理由を確認します。本文のコードは固定した環境で検証し、型やゴールの表示を省略・要約するときはその旨を示します。詰まった瞬間の感情を包み隠さず書きます。ClaudeというAIに質問した実際のやり取りをスクリーンショット付きで収録します。「正しいコード」だけでなく「なぜそのコードが正しいのか」を、数学者の言葉で翻訳しながら説明します。

証明を書くことは、一人で黙々とやる孤独な作業である必要はありません。本書では一貫して、AIを、説明や補題の候補を提案する相談相手として使います。

## 掲載コードの読み方

コード欄の見出しは、次の4種類です。

| 表示 | 使い方 |
|---|---|
| 完成例・確認コマンド | 証明・定義・型の確認です。各章に書いたimportや先行する宣言などの前提を揃えて実行します。`#check`や`#print`の成功自体は、新しい定理の証明ではありません。 |
| 断片 | 本文で指定した前後のコードと連結するか、指定位置に挿入します。単独では実行しません。 |
| 意図的なエラー例 | 説明のために失敗させる例です。完成例とは別のファイルで試してください。 |
| 未完成の骨格・練習問題 | `sorry`などを自分で埋める例です。解答を読む前に試せます。 |

`No goals`はカーソル位置のゴールが閉じたことを示します。証明の完成を判断するときは、エラー・警告、公理への依存、命題の数学的な意味も確認します。画面例は撮影時の記録で、固定した版の型やゴールは本文のコードと実出力を優先してください。

## 本書で得られる4つの実践的スキル

1. **Lean 4特有のエラー読解と「型」のメンタルモデル**：`definitionally equal`（定義的等値）の罠や、`failed to synthesize instance`（型クラスの探索失敗）など、初学者がつまずきやすいエラーの根本原因を理解し、パニックにならずに対処する論理的思考力を養います。
2. **AIの提案を検証しながら使う技術**：「文脈・エラー・意図」の3点セットを渡し、回答を診断や補題探索の候補として使います。質問を整えても誤りは起こり得るため、名前と型を調べ、証明をLeanで確認します。
3. **Mathlibの定義と定理を探す技術**：膨大な定理を暗記する必要はありません。Mathlibで利用できる探索タクティク `exact?` や `apply?` を使いこなし、タイムアウトした際はAIを意味検索エンジンとして用いて、目的の定理を自力で掘り当てる探索の手順を習得します。
4. **トップダウン型の証明構築術（`sorry` 駆動開発）** ：まず `sorry` で未証明の箇所を仮置きし、証明全体の設計図を作ります。残した課題が証明できるかを検討しながら、一つずつ証明で置き換える進め方を学びます。仮置きしたコードの型検査が通ることと、証明が完成することを区別します。
