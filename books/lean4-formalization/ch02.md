# 第2章：「型」という名の番人 〜型クラスという「免許証」の正体〜

[第1章](ch01)では `Goals accomplished!` を体験しました。そのとき使った `norm_num` や `ring` は、なぜ「効く」のでしょうか。なぜ `rfl` は `a + b = b + a` を証明できないのでしょうか。その答えはすべて「型」にあります。

本章は「完全に理解して暗記するための章」ではありません。[第3章](ch03)のエラー格闘編で詰まったとき、「あの話はここに書いてあった」と戻ってこられるインデックスを作ることが目的です。分からなくて当然ですので、流し読みで[第3章](ch03)へ進んでください。

## 2.0 本章のゴール ──── ゴール逆算型アプローチ

まず本章の終着点を見ていきます。以下のコードが理解・実行できることが本章のゴールです。

```lean:完成例・確認コマンド
import Mathlib

-- ゴール①：型クラスという「免許証」の確認
-- 数学：ℕ は加法を持つか？ / Lean：[Add ℕ] のインスタンスが存在するか？
#check (inferInstance : Add ℕ)
-- inferInstance : Add ℕ   ← 自然数には足し算の免許証がある

-- ゴール②：#print で型クラスの構造を解剖する
-- 数学：「加法を持つ」とはどういう構造か / Lean：Add クラスの定義を覗く
#print Add
-- class Add (α : Type u) where
--   add : α → α → α   ← 「add 演算が一つある」だけのシンプルな免許証

-- ゴール③：have によるサブゴール分割
-- 数学：「a ≤ b かつ b ≤ c ならば a ≤ c」を段階的に証明する
-- Lean：have でサブゴールを宣言し、linarith で解く
example (a b c : ℕ) (h1 : a ≤ b) (h2 : b ≤ c) : a ≤ c := by
  have step : a ≤ b := h1
  linarith
  -- No goals ✓
```

「なぜ `inferInstance` で免許証が取り出せるのか」「`#print` で何が見えるのか」「`have` でゴールをどう分割するのか」——これらを一つずつ見ていきます。

:::message
🔗 **[第3章](ch03)への伏線**

`#check (inferInstance : Add ℕ)` が成功するのは、Leanの環境に `Add ℕ` のインスタンス（免許証）が登録されているからです。逆に、登録されていない型でこれを試みると `failed to synthesize instance` という型クラスエラーが出ます。このエラーの正体と対処法を、[第3章](ch03)で正面から扱います。
:::

## 2.1 型の階層 ──── `Prop` と `Type` は何が違うか

Lean 4 のすべての項には**型**があります。

```lean:完成例・確認コマンド
import Mathlib
#check 42         -- 42 : ℕ
#check "hello"    -- "hello" : String
#check true       -- true : Bool
```

ここまでは普通のプログラミング言語と同じです。Lean 4 が決定的に異なるのは、**数学的な命題もまた型として扱われる**という点です。

```lean:完成例・確認コマンド
import Mathlib
#check (1 + 1 = 2)
#check (∀ n : ℕ, n ≥ 0)

-- 命題を型として、その項である証明を作る。
theorem proof_term_example : (0 : ℕ) = 0 := rfl

-- 整数が期待される文脈での自然数からの変換。
def natAsInt (n : ℕ) : ℤ := n
theorem natAsInt_eq (n : ℕ) : natAsInt n = Int.ofNat n := rfl
```

`Prop` は「命題の型」です。そして命題 `P : Prop` の**証明**とは、`h : P` という「`P` という型を持つ値」に他なりません。

数学とLeanの対応を整理します。

| 数学の概念 | Lean の表現 | 具体例 |
|---|---|---|
| 自然数の集合 $\mathbb{N}$ | `ℕ`（型） | `42 : ℕ` |
| 実数の集合 $\mathbb{R}$ | `ℝ`（型） | `3.14 : ℝ` |
| 命題 $P$ | `P : Prop` | `1 + 1 = 2 : Prop` |
| 命題 $P$ の証明 | `h : P` | `rfl : 0 = 0` |
| 「$P$ を証明せよ」 | `example : P := by ...` | ゴール = `⊢ P` |

「証明を書く」とは「命題 `P : Prop` 自体を型として、その項 `h : P` を構築すること」——この視点が、本章全体を貫く核心です。

:::message
**💡 数学学部生向け：型と集合の違い**

`Nat` と `Int` は別の型です。Leanでは自然数の項をそのまま整数の項と同一視せず、必要な場所に型変換（coercion）を挿入します。例えば整数が期待される位置では自然数から整数へ自動変換でき、`(n : ℤ)` と明示することもできます。数値リテラル `(42 : ℤ)` は最初から整数として解釈する指定です。
:::

:::message
**💡 プログラマ向け：Prop は Bool ではない**

`Prop` は `Bool`（`true`/`false`）とは別物です。`Bool` は実行時に計算できる真偽値ですが、`Prop` は真の命題も偽の命題も含む命題のソートです。`P : Prop` と書けることだけでは、`P` の証明があるとはいえません。`1 + 1 = 2 : Prop` を証明することと、`(1 + 1 == 2 : Bool)` を評価することは、全く異なる操作です。
:::

## 2.2 型クラスという「免許証」 ──── Lean の最も重要な抽象化

型クラスを一言で言うと、「この型はある演算を持っていますよ」という**免許証**です。

たとえば、足し算 `a + b` を書きたいとします。`a, b` がどんな型の値であっても、足し算が定義されていなければ計算できません。同じ型の元を足すこの例では `[Add α]` を与えます。`+` の記法自体は `HAdd` を通じて解釈され、`Add` のインスタンスから必要な `HAdd` を構成できます。

```lean:完成例・確認コマンド
import Mathlib
-- 数学：「型 α の値同士を足し算できる」という性質
-- Lean：Add α というクラスのインスタンスが存在すること
section
variable (α : Type) [Add α] (a b : α)
#check a + b  -- a + b : α   ← [Add α] が免許証として機能している
end
```

`[Add α]` という角括弧の記法が「免許証を要求する」シグナルです。

### `#print` で免許証の構造を解剖します

`#print Add` と入力すると、「足し算の免許証」の定義が覗けます。

```lean:完成例・確認コマンド
import Mathlib
#print Add
-- class Add (α : Type u) where
--   add : α → α → α
```

これだけです。`Add` は演算のデータを持つだけで、結合律や交換律の証明を要求しません。これらの法則は `AddSemigroup` や `AddCommMonoid` などで追加されます。Lean 4 の型クラスは、このような「最小の約束事」の積み重ねで構成されています。

:::message
**💡 `#print` で構造体を解剖する**

`#print` は型クラスだけでなく、構造体・定義・定理の内部を覗くための万能コマンドです。

```lean:完成例・確認コマンド
import Mathlib
#print Monoid
-- 継承の要約（npow の既定値などは省略）：
-- class Monoid (M : Type u) extends Semigroup M, MulOneClass M where ...
-- Semigroup が結合律、MulOneClass が単位元の法則を持つ。
#check @mul_assoc
#check @one_mul
#check @mul_one
```

モノイドの乗法と結合律は `Semigroup`、単位元とその法則は `MulOneClass` から引き継がれます。演算だけを持つ `Mul` と、法則の証明も含む構造を区別しましょう。
:::

:::message
**💡 プログラマ向け：型クラスとインターフェースの違い**

Java や TypeScript の `interface` に似ていますが、型クラスには**自動的なインスタンス解決**があります。例えば `inferInstance : Add ℕ` を要求すると、Leanが現在の環境から登録済みのインスタンスを探します。宣言の引数としての `[Add α]` は、呼び出し時にこの探索で補える引数を表します。明示的に実装クラスを渡す必要がない点が、インターフェースとの大きな違いです。この「自動的に」探してくる仕組みが、型クラスを「免許証」たらしめています。
:::

:::message
**🔢 数学学部生向け：型クラスと代数構造の対応**

数学での「群・環・体」という階層は、Lean では型クラスの継承として実装されています。`Field`（体）のインスタンスは `Ring`（環）のインスタンスでもあり、さらに `AddCommGroup`（加法可換群）のインスタンスでもあります。抽象的な型 `K` でも `[Field K]` を仮定すれば、体の加法・乗法・逆元・分配則を使えます。具体的な実数には、Mathlibが通常の体構造を登録しています。これが「免許証の階層」という抽象層を一枚挟んだことで、実数の証明でも抽象的な体の証明でも同じコードが使える理由です。
:::

## 2.3 `inferInstance` と `#check` ──── 免許証を手で確認する

型クラスのインスタンスが存在するかどうかを確認するには、`inferInstance` が使えます。

```lean:完成例・確認コマンド
import Mathlib
#check (inferInstance : CommSemiring ℕ)
#check (inferInstance : Field ℝ)
#check (inferInstance : LinearOrder ℝ)
#check (inferInstance : IsStrictOrderedRing ℝ)
-- 表示はいずれも inferInstance : 指定した型。
-- 順序と代数構造、および両者の整合性を分けて確認する。
```

`inferInstance` が成功すれば「現在の環境からその型クラスのインスタンスを構成できる」ことが確認できます。失敗すればエラーが出ます。これは現在の環境で探索できなかったということで、数学的にその構造が存在しない証明ではありません。

:::message alert
**💀 `failed to synthesize instance` エラーの正体**

これは[第3章](ch03)で最頻出のエラーです。「現在の環境で指定したインスタンスを構成できない」という意味です。必要な仮定やimportが不足している場合もあります。まず数学的に必要な仮定と、必要なimportを確認します。対処の例は次のとおりです。

1. `variable (α : Type) [Add α]` のように角括弧で免許証の要求を追加する
2. 具体的な型を意図していた場合は、その型を明記する。一般の定理を証明したい場合は、具体例に狭めず必要な構造を仮定する

[第3章](ch03)では、このエラーが実際に登場する場面を実況中継します。
:::

## 2.4 `simp` タクティク ──── 自動整理の魔法と罠

`simp`（simplify）は、定理データベースを使って式を自動的に簡約するタクティクです。

```lean:完成例・確認コマンド
import Mathlib

-- 数学：0 + n = n（加法の左単位元）
-- Lean：simp が Nat.zero_add を自動適用する
example (n : ℕ) : 0 + n = n := by
  simp
  -- No goals ✓
```

**実況中継：**

```text
-- simp 適用前の InfoView
n : ℕ
⊢ 0 + n = n

-- simp 適用後の InfoView
Goals accomplished!
```

`0 + n` は `Nat.zero_add` という `@[simp]` タグ付きの補題が自動適用されて `n` になります。

:::message alert
**💀 simp は万能ではない：ループと `simp only`**

`simp` が無限ループ（終わらない）を起こすことがあります。複数の補題が互いを書き換えし合う状況で起きます。

対処法は `simp only [補題名]` で使う補題を限定することです。

```lean:完成例・確認コマンド
import Mathlib
-- ループが心配なとき：使う補題を明示する
example (n : ℕ) : 0 + n = n := by
  simp only [Nat.zero_add]
  -- No goals ✓
```

どの補題が効いているか分からないときは `simp?` タクティクを使うと「実際に使われた補題の一覧」が提案されます。探索が成功した場合は、その提案を同じ文脈で再実行して確認できます。`simp?` も簡約処理を行うため、処理が終わらない場合の万能な解決策ではありません。
:::

## 2.5 `have` によるサブゴール分割 ──── 証明の設計図を作る

複雑な証明を「小さなステップの積み上げ」で解決するための道具が `have` です。数学での「まず補題を示す。次にその補題を使って…」という論法を、そのまま Lean に翻訳できます。

```lean:完成例・確認コマンド
import Mathlib

-- 数学：a ≤ b かつ b ≤ c かつ c ≤ d ならば a ≤ d（3段の推移律）
-- Lean：have で中間ステップを明示する
example (a b c d : ℕ) (h1 : a ≤ b) (h2 : b ≤ c) (h3 : c ≤ d) : a ≤ d := by
  -- ステップ①：a ≤ c を先に示す（have で宣言）
  have hac : a ≤ c := by linarith
  -- ステップ②：a ≤ c と c ≤ d から a ≤ d
  linarith
  -- No goals ✓
```

**実況中継：**

```text
-- have hac 宣言直後の InfoView
a b c d : ℕ
h1 : a ≤ b
h2 : b ≤ c
h3 : c ≤ d
hac : a ≤ c      ← have で宣言した補題がコンテキストに追加される
⊢ a ≤ d

-- linarith 適用後
Goals accomplished!
```

`have hac : a ≤ c` を宣言すると、その証明義務が新しいサブゴールとして現れ、証明が完了するとコンテキストに `hac : a ≤ c` として追加されます。

:::message
**💡 have は「証明の設計図」の基本単位**

[第5章](ch05)では `sorry` と `have` を組み合わせた「`sorry` 駆動開発」を学びます。まず大きな証明の論理構造を `have` で骨格化し、各 `have` を `sorry` で仮置きしてから、ステップ一つずつ穴を埋める——これが長い証明を攻略する戦略的なアプローチです。
:::

## 2.6 まとめ ──── 第2章の全対応表と練習問題

### 数学とLeanの対応を表にまとめます

| 数学の概念 | Lean の表現 | 備考 |
|---|---|---|
| 命題 $P$ | `P : Prop` | `1 + 1 = 2 : Prop` |
| 命題の証明 | `h : P` | `h : a ≤ b` |
| 型クラス（代数構造） | `class C (α : Type) where ...` | 「免許証」の本体 |
| 型クラスのインスタンス | `instance : C ℕ := ...` | Mathlib が事前登録 |
| インスタンスの確認 | `inferInstance` | `#check (inferInstance : Add ℕ)` |
| 構造体の内部確認 | `#print C` | `#print Add` で定義を覗く |
| 暗黙の型クラス要求 | `[Add α]` | 角括弧＝免許証の要求 |
| `simp` による自動整理 | `simp` / `simp only [...]` | `@[simp]` タグ付き補題を適用 |
| サブゴール宣言 | `have h : P := by ...` | 中間命題をコンテキストに追加 |
| 数値等式の自動証明 | `norm_num` | 具体的な数の計算 |
| 代数的等式の自動証明 | `ring` | 多項式・環の公理 |
| 線形不等式の自動証明 | `linarith` | 仮定を組み合わせる |
| 構造の内部定義を確認 | `#print 定義名` | 型クラス・定理すべてに使える |

**問1（易）：`#check` で型クラスのインスタンスを確認してください。**

```lean:完成例・確認コマンド
import Mathlib
-- 問：ℤ（整数）は CommRing（可換環）のインスタンスか？
-- #check と #print を使ってインスタンスと構造を確認してください。
#check (inferInstance : CommRing ℤ)
#print CommRing
```

:::details ヒントを見る

`inferInstance` に型クラスを指定すると、Lean が Mathlib から該当のインスタンスを探してきます。成功すればインスタンスの型が InfoView に表示されます。`#print CommRing` で CommRing の定義を解剖してみましょう。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib
-- ℤ は CommRing のインスタンスを持つ
#check (inferInstance : CommRing ℤ)
-- inferInstance : CommRing ℤ   ← Mathlib が登録したインスタンス

-- CommRing の構造を解剖する
#print CommRing
-- class CommRing (α : Type u) extends Ring α, CommMonoid α
-- → Ring（環）と CommMonoid（可換モノイド）の両方を継承している
-- No goals ✓
```

この `#check` で確認できるのは、`CommRing ℤ` のインスタンスを探索できることです。表示された `inferInstance` を具体的なインスタンスの宣言名と読み替えないでください。`extends Ring α` とあるため、`CommRing` のインスタンスがあれば自動的に `Ring` のインスタンスも使えます——免許証の階層構造です。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
#check (inferInstance : Ring ℤ)
#check (inferInstance : AddCommGroup ℤ)
#check (inferInstance : LinearOrder ℤ)
#check (inferInstance : IsStrictOrderedRing ℤ)
```

`inferInstance` を複数並べることで、一つの型がどれだけ多くの「免許証」を持っているかを確認できます。
:::

**問2（中）：`simp` を使って次の等式を証明してください。**

```lean:未完成の骨格・練習問題
import Mathlib
-- 数学：n + 0 = n（加法の右単位元）
theorem add_zero_exercise (n : ℕ) : n + 0 = n := by
  sorry -- ここを埋める
```

:::details ヒントを見る

`simp` タクティクを試してみましょう。`Nat.add_zero` という補題が `@[simp]` タグを持っているため、`simp` が自動的に適用します。`simp only [Nat.add_zero]` という形でも同じ結果が得られます。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib
example (n : ℕ) : n + 0 = n := by
  simp
  -- No goals ✓
```

`simp` を選んだ理由：`n + 0 = n` は `Nat.add_zero` という `@[simp]` タグ付きの補題そのものです。`simp` がこの補題を自動的に発見して適用します。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
-- simp only で使う補題を明示する（ループ防止版）
example (n : ℕ) : n + 0 = n := by
  simp only [Nat.add_zero]
  -- No goals ✓

-- または exact を使って項モードで書く
example (n : ℕ) : n + 0 = n :=
  Nat.add_zero n
```

この例の `simp only [Nat.add_zero]` は使う補題を明示する書き方です。一般に補題を限定しても、選んだ規則によってはループし得ます。また `:= Nat.add_zero n` は証明項を直接渡す書き方で、`by exact Nat.add_zero n` は同じ項をタクティクで提出する書き方です。
:::

**問3（難）：`have` を使ってサブゴールに分割し、証明してください。**

```lean:未完成の骨格・練習問題
import Mathlib
-- 数学：a ≤ b かつ b < c ならば a < c（≤ と < の混合推移律）
theorem strict_trans_exercise (a b c : ℕ) (h1 : a ≤ b) (h2 : b < c) : a < c := by
  sorry -- have を使って証明してください
```

:::details ヒントを見る

`have` で中間命題を宣言してから `linarith` で解く方法を試してみましょう。コンテキストに `h1 : a ≤ b` と `h2 : b < c` があれば、`linarith` が線形算術として `a < c` を自動的に導きます。あるいは `lt_of_le_of_lt h1 h2` という Mathlib の補題を `exact` で使う方法もあります。
:::

:::details 解答を見る

```lean:完成例・確認コマンド
import Mathlib
example (a b c : ℕ) (h1 : a ≤ b) (h2 : b < c) : a < c := by
  -- have で「中間命題」の証明義務を明示する
  have key : a ≤ b := h1
  -- key : a ≤ b と h2 : b < c から linarith が a < c を導く
  linarith
  -- No goals ✓
```

`linarith` を選んだ理由：コンテキストに `h1 : a ≤ b` と `h2 : b < c` があれば、`linarith` が線形算術として `a < c` を自動的に導きます。`have key` は冗長ですが、論理の流れを段階的に確認する練習として有効です。
:::

:::details 別解を見る

```lean:完成例・確認コマンド
import Mathlib
-- Mathlib の lt_of_le_of_lt を直接 exact で使う
example (a b c : ℕ) (h1 : a ≤ b) (h2 : b < c) : a < c :=
  lt_of_le_of_lt h1 h2

-- または calc ブロックで段階的に書く
example (a b c : ℕ) (h1 : a ≤ b) (h2 : b < c) : a < c :=
  calc a ≤ b := h1
       _ < c := h2
```

`lt_of_le_of_lt` は「`≤` と `<` の推移律」を直接述べる Mathlib の補題です。`calc` ブロックは「$a \leq b < c$」という数学的な式変形をそのまま Lean に翻訳する読みやすい記法です。
:::

## 2.7 つまずきポイントQ&A

:::message
**📝 第2章 つまずきポイントQ&A**

**Q1. `rfl` を使ったら `not definitionally equal` と言われた**
→ `rfl` は「両辺が定義を展開すると文字通り同じ式になる」場合にのみ使えます。`a + b = b + a` のような交換法則は定義的な等値ではなく、対応する交換法則の定理を使うか、自然数や可換環など適切な構造があれば `ring` を使えます。まず型・仮定・主張の真偽を確認してから、主張に合う補題やタクティクを選びます。

**Q2. `by` の中でインデントがずれてエラーが出た**
→ Lean 4 はインデントに厳格です。`by` の後に続く同じブロックのタクティクは字下げを揃えます。`have ... := by` や分岐などの内側はさらに字下げします。VS Code でタブとスペースが混在していないか確認してください。タクティクが同じ行に続いていることが原因のこともあります。

**Q3. `failed to synthesize instance` エラーが出た**
→ 型クラスの「免許証」がない状態です。`variable (α : Type)` だけ宣言して `a + b` を書こうとしても、`α` に `[Add α]` という免許証がないためエラーになります。`variable (α : Type) [Add α]` と角括弧で要求を追加してください。

**Q4. `Type*` と `Type u` の違いが分からない**
→ `Type u` は宇宙レベル `u` の型の型です。`Type*` は新しい宇宙レベルの変数を導入する記法です。`Type u` を使う場合は `universe u` などで名前を宣言します。本書の例では、`Type*` は新しい宇宙レベルを使って型を一般化する記法として読んでください。

**Q5. `simp` でループが起きてタイムアウトした**
→ `simp only [...]` で使う補題を明示的に限定してください。`simp?` は簡約が成功した場合に使う補題の候補を示しますが、それ自体も簡約処理を行います。循環が疑われるときは、新しく加えた規則やその向きを調べ、必要な規則だけで再実行してください。
:::

「型クラス＝免許証」という比喩は、Lean 4 の設計思想を最初に理解しようとした時に自然と浮かんだものです。`[Add α]` と書いた瞬間、「この型には足し算の演算が与えられている」という感覚が伴うようになり、エラーメッセージが読めるようになってきました。

本章で最も伝えたかったのは、「型クラスは暗記するものではなく、`#print` で覗くものだ」ということです。[第3章](ch03)では、この免許証の仕組みを知っているかどうかが、エラーとの格闘で決定的な差を生みます。

次の[第3章](ch03)では、いよいよ本格的なエラーと向き合います。「なぜ `ring` が使えないのか」「Claude をメンターとしてどう質問するか」——第2章で作ったインデックスが、そこで生きてきます。
