AIに証明を相談すると、それらしい定理名が返ってくることがあります。ところが、コードに貼り付けると `Unknown identifier` や `Unknown constant`。別の名前を聞き直しても、また同じエラーになる。

ここで一度、名前を当てる作業を止めてみます。確認したいのは、**その名前が今の環境で使えるか、使えるなら何を証明する定理なのか**です。

この記事では、自然数の加法の交換法則を題材に、名前・名前空間・import・版の順で確認します。最後に、見つけた定理を実際のゴールへ適用します。

:::message
掲載コードはLean 4.29.0-rc6で確認しています。今回実行する例はLean標準の機能だけで動き、Mathlibのimportは不要です。Mathlibを使うプロジェクトでの調べ方も後半で説明します。
失敗例と成功例は、別ファイルで試してください。
:::

## 1. まず、提案された名前だけを確認する

次は説明用に意図的に誤った名前です。実際のAIの回答を引用したものではありません。

```lean
-- 意図的な失敗例
#check Nat.add_comm_wrong
```

このコードは、指定した名前が見つからず失敗します。確認環境では、エラー本文に ``Unknown constant `Nat.add_comm_wrong` `` と表示されました。名前や文脈によって `Unknown identifier` と表示される場合もあります。`#check` は、渡した式をLeanが受け付けるか確認し、その型を表示する命令です。

この時点で分かるのは、「この場所、この環境では、その名前を解決できなかった」ということです。まだ、AIが存在しない名前を作ったと断定はできません。誤記、名前空間の省略、必要なファイルの読み込み不足、版の違いでも、名前が見つからなくなるからです。[Lean公式のエラー解説](https://lean-lang.org/doc/reference/latest/Error-Explanations/About___--unknownIdentifier/)も、名前空間やimport、変数のスコープを確認事項に挙げています。

長い証明の途中で困ったら、まず元のファイルの、問題の定理宣言の直前などで `#check` を試します。別ファイルへ切り出すなら、**同じプロジェクト内**に置き、必要なimport、自作の定義、`namespace`・`open`・`section` の文脈も残してください。文脈を落とすと、切り出したこと自体が別のエラーの原因になります。

なお、証明の中の仮定 `h` や `have` で作った名前は、その外の `#check` からは参照できません。それらが見つからない場合は、まず名前を使える範囲を確認します。以下では、ライブラリやファイルに宣言された定理名を扱います。

## 2. 正しい名前と名前空間を確認する

自然数の加法の交換法則には、`Nat.add_comm` が使えます。

```lean
#check Nat.add_comm
```

確認環境では次の型が表示されます。

```text
Nat.add_comm (n m : Nat) : n + m = m + n
```

名前の先頭の `Nat` は名前空間です。`Nat.add_comm` まで含めて、定理の名前として確認します。候補はエディタの補完、ライブラリのソース、ドキュメントから探せます。例えば、補完で `Nat.add_` に続く候補を調べ、`add_comm` の型が加法の交換法則を表しているかを読みます。

今回の `Nat.add_comm` はMathlib固有の定理ではなく、Lean本体の `Init/Data/Nat/Basic.lean` に宣言されています。Mathlib内を検索して見つからなくても、Lean本体にある可能性があります。ソースの場所が分かれば、その宣言と型を直接確認できます。

名前空間と短い名前の関係を、小さな自作定理で試してみましょう。

```lean
namespace ArticleDemo

theorem add_swap (a b : Nat) : a + b = b + a := by
  exact Nat.add_comm a b

end ArticleDemo

#check ArticleDemo.add_swap

open ArticleDemo in
#check add_swap
```

最初の `#check` は完全な名前を使います。後半の `open ArticleDemo in` は、直後のコマンドで名前空間を開き、短い名前を使えるようにしています。

調査中は、まず完全な名前で確認すると、何を参照しているかが明確になります。実は今回の `Nat.add_comm` は `protected` として宣言されているため、次の短い書き方は、この標準環境では失敗します。

```lean
-- 意図的な失敗例：上の成功例とは別ファイルで実行
open Nat in
#check add_comm
```

この場合は `Nat.add_comm` と書けば確認できます。`open Nat` だけで常に接頭辞を省けるわけではありません。

## 3. `open` と `import` を区別する

`open` は、未読込の定理を読み込む命令ではありません。

| 確認するもの | 役割 |
|---|---|
| `import` | 定義や定理を含むモジュールを読み込む |
| `open` | 読み込まれた名前を、名前空間の接頭辞を省いて参照しやすくする |

Mathlibの定理を調べるときは、ドキュメントやソースで**どのファイルに宣言されているか**も確認します。その定理を含むモジュールが読み込まれていなければ、完全な名前を書いても使えません。

Mathlibを導入済みのプロジェクトなら、調査用の別ファイルの先頭に `import Mathlib` を置き、候補の完全な名前を `#check` して、読み込み範囲の違いを切り分ける方法があります。これはMathlibをインストールする操作ではなく、現在のプロジェクトにあるMathlibを読み込む操作です。

importを足して名前が解決できたら、読み込み不足が原因だった可能性があります。一方、import自体が「モジュールが見つからない」などで失敗した場合は、定理名の確認まで進めていません。プロジェクトの開き方や依存関係の準備を先に確認します。

名前空間とファイル名は同じとは限りません。`Nat` で始まる定理だからといって、名前をそのままimport先へ変換できるわけではありません。[公式のモジュール解説](https://lean-lang.org/doc/reference/latest/Source-Files-and-Modules/)でも、ファイルと名前空間は別の仕組みとして説明されています。

## 4. Webの説明と手元の版を照合する

Web上では定理が見つかるのに、手元では名前が解決できない場合もあります。次に見るのは、使っている版です。まずエディタで目的のプロジェクトのフォルダを開いているか確認します。端末では、そのフォルダで `lake env lean --version` を実行し、プロジェクトが使うLeanの版を調べます。このコマンド自体が失敗した場合も、定理名の問題とは分けて扱います。

- `lean-toolchain`：プロジェクトが指定するLeanの版。
- `lake-manifest.json`：Mathlibを使っている場合、その依存項目の `rev`。
- 手元のソース：その版に目的の宣言があるか。既定の配置で取得済みなら、Mathlibは `.lake/packages/mathlib/` にあります。ローカル依存など別の配置なら、プロジェクトの指定先を確認します。

最新のWebドキュメントに載っていることと、固定した過去の版で使えることは別です。逆に、名前の解決に失敗しただけで「古い版だから」と決めつけることもできません。

まず手元のソースで、完全な名前だけでなく短い宣言名や関係する数学用語を検索します。名前空間の内部では接頭辞を省いて宣言されていることがあるためです。見つからなければ、参照しているドキュメントの版と比較します。エラーを一つ消すために、すぐプロジェクト全体を最新版へ更新する必要はありません。

## 5. 名前が見つかったら、型を読んで使う

`#check` が通れば、名前の確認は一歩前進です。次は、表示された型の対象・仮定・結論を読みます。

`Nat.add_comm` は、自然数 `n` と `m` に対して `n + m = m + n` を示す定理です。いまの目的が自然数の加法の交換法則なら、そのまま適用できます。

```lean
theorem article03_add_comm (a b : Nat) : a + b = b + a := by
  exact Nat.add_comm a b

#print axioms article03_add_comm
```

この証明は固定環境で成功し、`#print axioms` で公理への依存がないことも確認しました。`exact` は、渡した証明で現在のゴールを閉じます。別の定理に公理が表示されること自体が誤りという意味ではありません。

この段階では、元の主張が変わっていないことも確認します。名前を見つけるために対象を別の型へ変えたり、余分な仮定を足したりしていれば、最初に解きたかった問題とは違うかもしれません。

`#check` で名前と型を確かめることと、その定理を使って目的の証明を完成させることを、ここまでの二段階として扱うと整理できます。

## AIへ聞き直すなら、名前の根拠も添えてもらう

名前が見つからなかったときは、別名だけを求めるより、確認した情報をまとめて返します。

```text
提案された定理名が、手元の環境で解決できません。

Leanの版（確認したプロジェクトも）：
Mathlibのrev（使用する場合）：
必要なimport・namespace・open・定義を含む再現コード：
#checkで確認した名前とエラー全文：
手元のソースで探した名前・語句と結果：
証明したい命題と仮定：

候補の完全な名前、宣言のあるファイル、型を示してください。
使用中の版で確認できていない点は、未確認と明記してください。
元の仮定と結論を保った使用例も示してください。
```

返ってきた参照先とコードは、手元でも確認します。質問全体の作り方は、[再現コード・エラー・数学的意図をそろえる記事](https://zenn.dev/matsuteru/articles/lean4-ai-type-error)で具体例とともに説明しています。

型や仮定を読み、Mathlibの補題を探して証明へつなげる練習を進めたい方は、Lean 4入門の第1巻もご覧ください。[無料の序文](https://zenn.dev/matsuteru/books/ab366ea6fa62f6/viewer/e8d7ab)から、学習の流れを確認できます。

参考資料は最新版の公式ドキュメントです。コードの確認には冒頭に示した固定版を使っています。
