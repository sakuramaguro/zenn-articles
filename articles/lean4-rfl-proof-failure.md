自然数の足し算では、順序を入れ替えても答えは変わりません。それなのに、Leanで次のように書くとエラーになります。

```lean
-- 意図的に失敗する例
example (a b : Nat) : a + b = b + a := by
  rfl
```

「正しい式なのに、なぜ証明できないのだろう？」と感じるかもしれません。

ここで分けたいのが、**今回の方法では証明できなかったこと**と、**命題そのものが偽であること**です。この等式は正しく、別の方法で証明できます。

この記事では、自然数の等式を3つ比べながら、`rfl` が失敗したときに何を確認すればよいかを整理します。

前回は、関数の定義を展開して `rfl` で証明できる例を扱いました。今回は、同じ方法では証明できない等式との違いを見ていきます。前回を読んでいなくても、以下の例だけで試せます。

:::message
コードはLean 4.29.0-rc6で確認しています。`Nat` は自然数の型です。今回の例にはMathlibのimportは不要です。
意図的な失敗例は、成功例とは別ファイルで実行するか、修正後のコードに置き換えてください。
:::

## 1. 計算すればそろう等式

まず、次の証明は通ります。

```lean
example : (1 : Nat) + 1 = 2 := by
  rfl
```

`example` の後ろに証明したい命題を書き、`by` の後ろで証明の手順を指定しています。`(1 : Nat)` は、ここで扱う1が自然数であることを明示しています。

この例では、Leanは自然数の足し算の定義に沿って左辺を計算し、右辺と同じになることを確認できます。このように、定義を展開したり計算したりすることで同じになることを、**定義的に等しい**といいます。

等式を扱う今回の例では、`rfl` はこの等しさを使って証明を完成させます。左右の文字列が同じかを見るだけではありません。`1 + 1` と `2` は見た目が違っても、この方法で証明できます。

一方、数学的に正しい等式が、すべてこの計算だけでそろうわけではありません。

## 2. 真でも `rfl` では閉じない等式

冒頭の例を実行すると、次のエラーが出ます。ファイル名と行番号を除いた出力の抜粋です。

```text
Tactic `rfl` failed: The left-hand side
  a + b
is not definitionally equal to the right-hand side
  b + a
```

注目するのは、`not definitionally equal` の部分です。ここでは、変数を含む `a + b` と `b + a` が定義に沿った計算ではそろわず、`rfl` でゴールを閉じられなかった、と読めます。

これは「加法の交換法則は偽だ」という通知ではありません。

そこで、数学で使いたい根拠をそのまま指定します。自然数の加法の交換法則は、Leanでは `Nat.add_comm` という名前で用意されています。

```lean
example (a b : Nat) : a + b = b + a := by
  exact Nat.add_comm a b
```

`Nat.add_comm a b` は、いま証明したい `a + b = b + a` の証明です。`exact` は、それを現在のゴールの証明として使います。

変更したのは `by` の後ろだけです。自然数を扱うことも、証明したい等式も変えていません。今回は、主張を直す必要はなく、使う証明の手段を選び直せばよかったわけです。

## 3. 主張そのものを見直す場合もある

では、次の例はどうでしょうか。

```lean
-- 意図的に失敗する例
example : (1 : Nat) + 1 = 3 := by
  rfl
```

これも `rfl` は失敗します。しかし、先ほどの交換法則とは事情が違います。自然数では左辺は2なので、そもそも等式が偽です。

ここで大切なのは、**`rfl` が失敗したから偽だと判断したのではない**という点です。自然数の計算を確認したことで、主張の誤りが分かります。

Leanでも、この等式の否定を証明できます。

```lean
example : (1 : Nat) + 1 ≠ 3 := by
  decide
```

`decide` は、このように真偽を計算で判定できる命題の証明に使えます。あらゆる数学の命題を判定できる万能の手段ではありません。

また、ここでは `= 3` を `≠ 3` に変えています。これは元の等式の証明が完成したのではなく、**別の、正しい主張を証明した**ということです。AIが修正コードを提案したときにも、証明したい命題まで変わっていないか確認しましょう。

## 4. 次に止まったときの確認順

別のタクティクを試す前に、次の3点を見直してみてください。

1. **どの型を扱っているか。** 今回はすべて自然数の `Nat` です。自分が意図した対象になっているか読みます。
2. **主張と仮定は意図どおりか。** 等号の向きや数字、必要な条件を確認します。小さな具体例や反例を考えることも役立ちます。
3. **どんな数学的根拠を使いたいか。** 計算でそろう等式なのか、交換法則のような定理を使う場面なのかを考えます。

この確認順だけで、すべての命題の真偽が分かるわけではありません。ただ、手段を変えるべき場面と、主張を見直すべき場面を混同しにくくなります。

判断に迷ってAIへ相談するときは、コードとエラーに加えて、「この等式を変えずに証明したい」という意図も添えます。質問の準備は、[前回の記事](https://zenn.dev/matsuteru/articles/lean4-ai-type-error)にまとめています。

## 確認問題：掛け算ならどう書く？

自然数の掛け算にも交換法則があります。`Nat.mul_comm` を使って、次の証明の `sorry` を置き換えてみてください。

```lean
-- 練習用：sorryを残した未完成の証明
example (a b : Nat) : a * b = b * a := by
  sorry
```

`sorry` は未証明の部分を仮置きするためのものです。残っている間は完成した証明として扱いません。

:::details 解答
```lean
example (a b : Nat) : a * b = b * a := by
  exact Nat.mul_comm a b
```

足し算の例と同じく、証明したい等式に対応する既存の定理を `exact` で使います。
:::
